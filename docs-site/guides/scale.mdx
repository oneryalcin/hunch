---
title: "Large datasets"
description: "What a 100,000-row run costs and how long it takes, and the settings that control speed, spend and memory."
---

hunch has been run on 100,000 Amazon product reviews with one yes/no question each ("Is this product review positive overall?", gold = the star rating). The example is in `prototype/examples/scale/`.

| | |
|---|---|
| Throughput | 96,000 requests in 27.8 minutes: 57.5 per second with 32 in flight |
| Failures | 32 network retries (0.03%), all recovered; nothing lost |
| Cost | $1.55 (compile estimated $1.72) |
| Store | +80 MB (about 840 bytes per answer, plus the results table); peak memory 566 MB |
| Re-run, all cached | `run` 4.1 s, `compile` 2.5 s |
| `test` | 4.8 s |
| Result | 97.0% accurate, AUROC 0.993; acting at 0.9 automates 76% of rows at about 0.5% error |

At that rate a million rows would take about five hours and cost about $16 with Jev.

## Estimate first

```sh
hunch compile .
```

`compile` counts what is cached and what is not, and prices the rest before anything is sent. Its estimate is usually a little high: it is computed from characters, and the engine bills tokens.

## Cap the spend

```sh
hunch run . --max-cost 2
```

`--max-cost` (or `HUNCH_MAX_COST`) refuses to ask when one judgment's missing answers are estimated to cost more than the cap, and asks nothing. Answers are saved as each request returns, so a run that stops partway (a crash, Ctrl-C, a network failure) keeps what it got; the next run asks only for the rest.

## Speed

Throughput is requests in flight divided by how long each takes, so it is set by concurrency, not by a rate limit. `HUNCH_CONCURRENCY` (default 16) is the number of requests in flight. In the 100k run, 16 gave 63 per second on a 2,000-row probe, 32 gave 57.5 per second over the full run, and 48 gave 84 per second on the probe. No request was rate-limited at any setting. Retries on rate limits, server errors and network failures back off and try again.

## Re-runs are cheap

Every row is hashed on every run and looked up in the cache in one pass. A fully cached 100k-row run took 4 seconds, so there is no incremental mode: change the source, and only new or changed rows are asked. `on_change: new_rows_only` keeps answers for rows that did not change even when the spec did; see [Change a spec](/guides/change-a-spec).

## Keep inputs small

Cost is almost all input tokens (Jev bills $0.042 per million; output is free). Send only the columns the question needs (`state`), cut long text with `clip`, and ask all of a row's questions in one spec: with Jev, they share one request.
