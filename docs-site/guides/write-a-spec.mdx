---
title: "Write a spec"
description: "Turn a judgment you make today into a spec: the rows, what the model sees, the question, and how to test it."
---

Start from a decision your software or your team already makes. Write down the question a careful person would answer for each row. The rest of the spec follows from that question: which rows it applies to, what someone needs to see to answer it, and how you would know the answer is right.

This page builds a spec in that order. The [spec reference](/reference/spec) lists every key.

## The rows

A spec needs one row per thing you judge, and a stable id for each row. hunch uses the id to match answers, reviews and diffs across runs.

```yaml
judgment: triage
model: jev-1.13.0
source: messages.csv
key: id
```

`model` names the [engine](/reference/engines) that answers. `source` can also read coding-agent sessions (`traces(<glob>)`) or call a Python function (`py(rows.py:load)`).

## What the model sees

`state` lists the columns sent with each question. Send what a person would need to decide, and nothing more. Extra columns cost tokens and give the model something to be distracted by.

```yaml
state: [subject, body]
```

To remove secrets or shorten long columns before they are sent, see `redact` and `clip` in the [spec reference](/reference/spec).

## The question

The model never sees the question's name. To it, `dept` means nothing, while "Which team should handle this support message?" means everything. Write `instructions` as the full question.

Then describe each option in `criteria`, including where the line between two options falls. These descriptions often matter more than the instructions do.

```yaml
questions:
  dept:
    type: choice
    instructions: Which team should handle this support message?
    criteria:
      billing: Money already charged or owed
      technical: Something broken in the product or API
      sales: Buying more or differently
    none: The message needs no team (thanks, spam, chit-chat)
```

The `none` line covers rows that fit no option. Without it, the model must pick one of your options, and it will pick one confidently.

Choose the type by what the answer means:

- `choice`: exactly one option applies.
- `noul`: a yes/no condition. The answer is the probability of yes, so 0.5 means "can't tell", not "somewhat".
- `score`: a position on an ordered scale. `criteria` is a list of levels, each described as a concrete situation.
- `multi`: any number of options can apply. hunch asks one yes/no question per option.

Ask one thing per question. "Is it urgent and about billing?" is two questions.

## How you will know it is right

If your data has an answer key, name its column in `gold`. Set `act`, the confidence below which a person should look. Put thresholds under `tests`, and `hunch test` fails when accuracy drops below them.

```yaml
questions:
  dept:
    # type, instructions, criteria as above
    act: 0.80
    gold: gold_dept
tests:
  dept:
    min_accuracy: 0.90
```

Without an answer key, leave `gold` out. You will review a random sample instead, and `test` estimates accuracy from it. See [Review](/guides/review).

Some cases must never go wrong, however good the average. Write them into the spec as [examples](/reference/spec#examples), rows with the answers they must get, and `test` checks each one:

```yaml
examples:
  - name: double charge
    row: {subject: Charged twice, body: "I was billed twice for March, please refund one."}
    expect: {dept: billing}
```

## Check it before it costs anything

```sh
hunch lint triage.yml       # structure, columns, limits
hunch compile triage.yml    # the exact request for the first row, and the cost
```

`lint` catches mistakes before any request is sent. Here, `state` lists `bdy` instead of `body`:

```
lint error: column 'bdy' does not reach this judgment (has ['id', 'subject', 'body', 'gold_dept'])
```

Then read the request that `compile` prints. It is exactly what the model will see. If you could not answer the question from it, the model cannot either.

## Start small

The first version of a question is rarely the best one, and every row asked under a changed question is paid for again. So run a sample first (`hunch run triage.yml --sample 50` asks about the same 50 rows every time, and leaves the full table alone), review twenty rows, and test before you run everything. [Change a spec](/guides/change-a-spec) shows how to compare versions.
