---
title: "Write a spec"
description: "Turn a judgment you make today into a spec: pick the rows, the question, what the model sees, and how to test it."
---

Start from a decision your software or your team already makes, and write down the question a careful person would answer for each row. The [spec reference](/reference/spec) lists every key; this page is about getting the first version right.

## 1. The rows

One row per thing you judge. Name a stable id column in `key`; hunch uses it to match answers, reviews and diffs.

```yaml
judgment: triage
source: messages.csv          # or traces(<glob>) for agent sessions, or py(rows.py:load) for anything else
key: id
```

## 2. What the model sees

`state` lists the columns sent with each question. Send what a person would need to decide, and nothing else: extra columns cost tokens and give the model something to be distracted by.

```yaml
state: [subject, body]
```

Two keys keep the input safe and small: `redact` (remove secrets, emails, home paths or your own patterns before anything is hashed or sent) and `clip` (keep the first or last N characters of a long column). Both are in the [reference](/reference/spec).

## 3. The question

Write `instructions` as the full question. The model does not read the question's name, so `dept` means nothing to it; "Which team should handle this support message?" does.

Describe each option in `criteria`, including where the line between two options falls. Most mistakes are between neighbouring options, so the descriptions matter more than the instructions.

```yaml
questions:
  dept:
    type: choice
    instructions: Which team should handle this support message?
    criteria:
      billing: Money already charged or owed
      technical: Something broken in the product or API
      sales: Buying more or differently
    none: The message needs no team (thanks, spam, chit-chat)
```

<Tip>
If some rows fit no option, add `none:` with a description of when nothing fits. Without it, the model has to pick one of your options and will do so confidently.
</Tip>

Pick the type by what the answer means:

- **`choice`**: exactly one option applies.
- **`noul`**: a yes/no condition. The answer is the probability of yes; 0.5 means "can't tell", not "somewhat".
- **`score`**: a position on an ordered scale. `criteria` is a list of levels, each described as a concrete situation.
- **`multi`**: any number of options can apply. hunch asks one yes/no per option.

Ask one thing per question. "Is it urgent and about billing?" is two questions.

## 4. How to test it

If your data has an answer key, name the column in `gold`. Set `act`, the confidence below which a person should look. Add thresholds under `tests` so `hunch test` fails when accuracy drops.

```yaml
    act: 0.80
    gold: gold_dept
tests:
  dept:
    min_accuracy: 0.90
```

No answer key? Leave `gold` out and review a random sample instead; `test` estimates accuracy from it. See [Review](/guides/review).

## 5. Check it before it costs anything

```sh
hunch lint triage.yml       # structure, columns, limits
hunch compile triage.yml    # the exact request for the first row, and the cost
```

`lint` catches mistakes before any request is sent. For example, a `state` column that is not in the source:

```
lint error: column 'text' does not reach this judgment (has ['id', 'subject', 'body', 'gold_dept', 'gold_topics'])
```

Read the request `compile` prints. It is exactly what the model will see; if you could not answer the question from it, neither can the model.

## 6. Run a sample first

Run, review twenty rows, and test before running everything. The first version of a question is rarely the best one, and every row you run twice under a changed question is paid twice. [Change a spec](/guides/change-a-spec) shows how to compare versions.
