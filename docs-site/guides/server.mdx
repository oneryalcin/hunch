title: "Run the server"
description: "Serve judgments over HTTP, review in the browser, and watch runs and drift, from the same specs and store as the CLI."
---

`hunch-server` is a small web app over your specs. It does three things:

- **Judges rows over HTTP** (`POST /v1/judge`), for apps not written in Python.
- **Shows the review queue in a browser**, one click per verdict, so people who don't use a terminal can build gold.
- **Shows runs and drift**: every run's cost and status, and whether a judgment's label mix changed between runs.

It reads the same spec files and the same store as the CLI. A row judged through the server is a cache hit for the next `hunch run`; a verdict clicked in the browser is used by the next `hunch test`.

## Start it

From a checkout of the repository:

```sh
cd server
HUNCH_PROJECTS=../prototype/examples HUNCH_SERVER_TOKEN=secret \
  uv run uvicorn hunch_server.app:app --port 8765
```

- `HUNCH_PROJECTS` is the folder of specs it serves. Every `path` in a request is relative to it, and anything that resolves outside it is refused.
- `HUNCH_SERVER_TOKEN` is the token every request must carry. Without it the server is open to anyone who can reach the port: use that only on your own machine.
- The store is found the same way as for the CLI: the nearest `.hunch/store.sqlite` above each spec, or `HUNCH_STORE`. See [Store](/reference/store#where-it-lives).
- The engine's API key (`TYPESAFE_API_KEY`, …) must be in the server's environment for rows it has not seen before.

Open `http://localhost:8765/?token=secret` for the list of projects.

## Judge a row

```sh
curl -H "Authorization: Bearer secret" -X POST localhost:8765/v1/judge \
  -d '{"path": "features/triage.yml",
       "row": {"subject": "Charged twice", "body": "I see two identical charges for March. Please refund one."}}'
```

```json
{"dept": {"label": "billing", "p": 1.0, "margin": 1.0, "route": "act", "cached": true},
 "topics__refund": {"label": "yes", "p": 0.99, "margin": 0.98, "route": "", "cached": true}, ...}
```

The answers are the same as [`hunch.judge`](/reference/python#judge). Add `"shadow": "<candidate path>"` to run a candidate spec on the same row after the response; see [Shadow mode](/guides/shadow).

The server caps what one request may spend: `HUNCH_SERVER_MAX_COST`, default `$0.01` per judgment. Above it, nothing is asked and the request gets `422`:

```json
{"error": "triage: would ask 7 answers in 1 requests (~$0.0000), above --max-cost $0.0; nothing asked"}
```

(That example ran with `HUNCH_SERVER_MAX_COST=0`.)

## Review in the browser

`http://localhost:8765/review?path=features&token=secret&reviewer=alice`

The page shows up to 25 rows from the same queue as `hunch review`: rows where the model disagrees with the answer key, random spot checks, then rows the model was unsure of. Each card has one button per verdict. Judge only from the text shown; if you can only decide because you know more than the page shows, click **needs more context**. Verdicts are appended to the judgment's `.reviews.csv` next to its spec, signed with `reviewer`, and the page reloads with the next rows.

The page only accepts a verdict for a row the queue is offering, as the kind it offers it (`409` otherwise), so spot checks stay a random sample.

## Runs and drift

- `http://localhost:8765/runs?path=features&token=secret`: every run of the project, with rows, answers asked, cost, model, spec hash, git commit and status, then the latest label mix of each question. A question whose mix moved by more than 0.10 since the previous run (total variation distance: the share of answers that would have to change label) is flagged.
- `GET /v1/drift?path=features&node=triage` returns the same numbers as JSON for alerts. See [Server API](/reference/server-api).

Drift compares label mixes between runs of the same judgment. It tells you the data or the spec changed, not which answers are wrong; review a sample to find out.

## What it does not do yet

- Run several server processes on one store beyond what SQLite's WAL mode allows.
- Reviewer accounts: the reviewer's name is a parameter, not a login.
- Postgres.
