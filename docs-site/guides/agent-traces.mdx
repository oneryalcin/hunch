---
title: "Judge agent traces"
description: "Read coding-agent sessions as rows and measure how each turn went: did it work, did the agent say it was done, was it right."
---

Agent sessions are the rows hunch was built for. Every turn has a request, the agent's final reply, and what the developer wrote next. The next message is the closest thing to free gold in a conversation: "thanks, now do X" means the turn worked, "still broken" means it failed.

## Point a spec at sessions

```yaml
source: traces(sessions/*/*.jsonl)    # a glob, relative to the spec; ~ works
view: turns                           # or runs: one row per session
```

The format is detected from each file:

| Format | Files |
|---|---|
| Claude Code | session `.jsonl` files (`~/.claude/projects/<project>/<session>.jsonl`) |
| Cursor | agent `.jsonl` transcripts |
| OpenCode | session `.json` files |
| OpenTelemetry GenAI | spans with `gen_ai.input.messages` / `gen_ai.output.messages`, one trace per line or a list of spans (Langfuse and other OTel-based tools export this) |

Each view gives these columns:

| View | One row per | Columns |
|---|---|---|
| `turns` | human message | `id`, `session`, `at`, `request`, `final_reply`, `next_message`, `tools`, `edits`, `ran_after_edit` |
| `runs` | session | `id`, `session`, `at`, `request`, `final_messages`, `human_messages`, `tools`, `edits`, `ran_after_edit` |

`tools` and `edits` count the agent's tool calls and file edits; `ran_after_edit` says whether it ran anything after its last edit. Text the harness injects into a human message (IDE context, `!` shell output, system reminders, messages from other agent sessions) is removed, so `request` and `next_message` are what a person typed.

Look at the rows before you write a spec:

```sh
uvx --from git+https://github.com/oneryalcin/hunch python -m hunch.traces 'sessions/*/*.jsonl' turns
```

```
309 rows
{'id': '07b57159#1', 'request': 'Today, our target is to reach till milestone 3, also note, for the github versio', 'final_reply': "Milestones 1–3 complete. Here's what was built and verified: …", 'next_message': 'now organize test files properly into a directory and do milestone 4, skip miles', 'tools': 49, 'edits': 26, 'ran_after_edit': 'no'}
```

## Keep private things private

Sessions contain paths, emails, keys and whatever else you pasted. `redact` removes them from every `state` column before it is hashed, sent to the engine or logged; `clip` keeps long fields to a size. The judgment's results table in `.hunch/store.sqlite` keeps the row as read, unredacted, like any copy of your data: keep `.hunch/` out of git.

```yaml
redact: [secrets, emails, home, "[0-9]{1,3}([.][0-9]{1,3}){3}"]   # built-ins, plus IPv4 addresses
clip: {request: 3000, final_reply: -3000, next_message: 1500}   # -N keeps the last N characters
```

Run `hunch compile` and read the request it prints: it is exactly what will leave your machine. The redacted text is still sent to the engine, so check what else is in it first.

<Warning>
In YAML, backslashes inside double quotes are escape characters: `"\d"` is an error. Use single quotes for regular expressions (`'\d+'`) or avoid backslashes (`[0-9]`).
</Warning>

## Two judgments that work together

`outcome` reads your next message; `claims` reads only the agent's final reply, so it can run live, the moment the turn ends. Together they answer: when the agent says it is done, is it?

```yaml outcome.yml
judgment: outcome
source: traces(sessions/*/*.jsonl)
redact: [secrets, emails, home]
clip: {request: 3000, final_reply: -3000, next_message: 1500}
key: id
state: [request, final_reply, next_message]
questions:
  outcome:
    type: choice
    instructions: >-
      A developer asked a coding agent for something (`request`). `final_reply` is the agent's last message
      for that turn and `next_message` is what the developer wrote next. Judging mainly from `next_message`,
      how did the agent's turn go?
    criteria:
      worked: The developer accepts the result or moves on (thanks, approval, a next step that builds on it, a new unrelated task)
      failed: The developer reports it did not work (the same or a new error, a bug, wrong output, "still broken", or pastes an error log). A follow-up question (asking to explain, compare or recommend) is not a failure
      redirected: The developer says the agent misunderstood, took the wrong approach, or should stop or undo; an interruption counts
      unclear: The next message does not show whether the turn worked, such as a follow-up question about the answer
    act: 0.60
```

```yaml claims.yml
judgment: claims
source: traces(sessions/*/*.jsonl)
redact: [secrets, emails, home]
clip: {request: 3000, final_reply: -3000}
key: id
state: [request, final_reply]
questions:
  claims_done:
    type: noul
    instructions: >-
      In `final_reply`, does the agent state or clearly imply that what the developer asked for in `request`
      is done and working? A plan, a question back, a partial result, or a report that it could not do it is "no".
```

Run both, then join the two tables in the store:

```sh
hunch run . --max-cost 1
sqlite3 -header -column .hunch/store.sqlite \
  "select c.claims_done, o.outcome, count(*) n from claims c join outcome o using(id) group by 1, 2"
```

## Review from the text, not from memory

If these are your own sessions, you remember what happened next; the model does not. Grade only from what the review screen shows, and press `c` (needs more context) when only your memory decides it. `hunch test` then reports how often the input was not enough, which tells you whether to give the spec more of the session. See [Review](/guides/review).

## What it measured

On 533 turns from the maintainer's own Claude Code sessions, with the earlier version of `outcome` (about $0.04 for both judgments with Jev; recorded in `docs/04-design.md`, round 15):

- `outcome` was right on an estimated **92.9%** of turns (95% CI 77–98%), from 28 randomly chosen turns reviewed by the developer who wrote them (the review screen shows the model's answer). Every reviewed answer with confidence 0.6 or above was right, 23 of 23.
- Only 1 of 30 random turns needed more context than request, reply and next message.
- When the agent said it was done, the next message said it had failed or been redirected on 3% of turns (7 of 227). When it did not say so, 8% (26 of 306). `claims` has not been reviewed yet, so these rates rest on its unreviewed answers.

On the public [Trace Commons](https://huggingface.co/datasets/trace-commons/agent-traces) Claude Code sessions (309 turns, CC BY 4.0), the example's earlier version of these specs (`prototype/examples/claude_code/`: `act` 0.80, without the follow-up-question lines) scored 90% (`outcome`) and 88% (`claims`) against a blind panel of three AI reviewers. The example is in `prototype/examples/claude_code/`.
