```bash
hunch <command> <path> [flags]
hunch init [--list] RECIPE [DIR]
```

`path` is a spec file (`intent.yml`) or a folder of specs (a project). Every command loads and lints the whole project first: lint warnings print to stderr, and a lint error stops the command with exit code 2.

## Commands

| Command | What it does | Asks the engine? |
| --- | --- | --- |
| `lint` | Checks the specs and prints `lint: ok (N judgments)` | No |
| `compile` | Shows one real request and what `run` would ask and cost | No |
| `run` | Answers every row, caches the answers, writes one table per judgment | Yes, missing answers only |
| `test` | Scores the answers against gold and checks the `tests:` thresholds | Yes, missing answers only |
| `review` | Walks you through the rows that need a human verdict | Yes, missing answers only |
| `diff` | Compares this spec with an older or other version on today's rows | Yes, missing answers only |
| `suggest` | Asks an LLM to rewrite one question and keeps a rewrite only if it wins | Yes (writer and new answers) |
| `init` | Copies a starter recipe into a folder | No |

Answers are cached by content, so any command that asks only pays for answers the store doesn't have. Put `--max-cost 0` on a command to be sure it spends nothing: if anything is missing, it stops before asking. For `suggest`, the cap also covers each writer call at its worst case (the whole reply allowance).

### `hunch init`

```bash
hunch init --list               # the recipes, one line each
hunch init tickets              # copies the recipe into ./tickets
hunch init agent-eval evals/    # copies into evals/
```

The folder must not exist yet. Recipes today: `agent-eval` (check a coding agent's work from its trace) and `tickets` (route 40 sample support tickets; about $0.001 to run).

## Flags

| Flag | Used by | Default | What it does |
| --- | --- | --- | --- |
| `--node NAME` | `run`, `test`, `diff`, `review`, `compile`, `suggest` | all (`run`, `test`), required when a project has several judgments (`review`, `suggest`) | One judgment in a project. `run --node X` runs X and the judgments it reads from. |
| `--against REF` | `diff`, `review` | none | `diff`: the old version, a spec/folder path or `git:REF` (for example `git:HEAD~1`); with `--model` and no `--against`, the same specs on their own engine. `review`: put rows where that version answers differently first |
| `--source CSV` | all | the spec's `source` | Run the root judgments on this CSV instead (a holdout set, for example) |
| `--traffic` | all | off | Run the root judgments on rows logged by `judge(..., shadow=...)`. Not with `--source` |
| `--model ID` | all | the spec's `model` | Use this engine for every judgment. Its tables get a suffix (`intent__deepseek_deepseek_flash`), so the spec's own tables are untouched |
| `--max-cost USD` | all | `$HUNCH_MAX_COST`, else no cap | Stop before asking if one judgment's missing answers would cost more than this (estimated) |
| `--allow-change` | `run` | off | Accept a changed spec under `on_change: freeze` |
| `--list` | `review` | off | Print the queue instead of prompting |
| `--limit N` | `review` | no limit | At most N rows this session |
| `--audit N` | `review` | 30 | Random rows to spot check per question, counting ones already reviewed |
| `--reviewer NAME` | `review` | your login name | Name saved with each verdict |
| `--question QID` | `suggest` | required if the spec has several questions | The question to rewrite |
| `--n N` | `suggest` | 3 | Rewrites to try |
| `--writer MODEL` | `suggest` | `deepseek:deepseek-flash` | The LLM that writes rewrites |

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | Done. For `test`: every check passed |
| 1 | `test`: at least one `FAIL` line. Any command: stopped with a message (above `--max-cost`, `on_change: freeze` refused, unknown judgment) |
| 2 | Lint error in a spec, or bad arguments |

<Warning>
`test` exits 1 both when a check fails and when `--max-cost` stops it from asking (for example, `order_stability` needs new answers). Read the last line of output to tell them apart.
</Warning>

## Reading the output

### `compile`

```text
# intent: request for row 1 (one request per row, all questions read once)
{
  "model": "jev-1.13.0",
  "state": {
    "text": "I still have not received my new card, I ordered over a week ago."
  },
  "questions": { "intent": { "type": "choice", ... } }
}

# intent: 770 rows in; 770 answers planned, 770 cached, 0 to ask, ~0 input tokens, ~$0.00000 (jev-1.13.0)
```

- The JSON is the exact request for the first row, after `redact` and `clip`. What you see is what the engine sees. For an LLM engine it prints the prompt instead.
- Then one line per judgment: rows in, answers planned, how many are cached, how many `run` would ask, and the estimated tokens and cost.
- `where keeps ≤ N` and `rows kept because the answers their where-clause needs aren't cached yet`: the upstream judgment hasn't run, so the count and cost are an upper bound. Run the upstream judgment first for the real numbers.
- `size warning`: a row's state is near the engine's size limit.
- `on_change: freeze and the spec changed`: `run` will refuse without `--allow-change`.
- `# total`: the whole project, with an expected cost when some rows are an upper bound.

### `run`

```text
intent: 385 rows in; answers: 385 cached, 0 asked in 0 requests, 0 input tokens, $0.00000
  intent: 74 rows below act=0.9 → review queue
materialized 1 table(s) in .hunch/store.sqlite (run 2026-09-25T10:45:03-8b2bab)
```

- Answers cached and asked, requests, input tokens and the real cost.
- `rows below act`: answers whose confidence is under the question's `act` threshold. Your code should not act on them alone; they are what `review` shows as "model unsure".
- The run id ties every table row to this run (see [Store](/reference/store)).

While asking, stderr shows progress: `asking 529 answers in 529 requests (~$0.0168)` and the request rate.

### `test`

Real output, BANKING77 holdout (`hunch test intent.yml --source banking77_holdout.csv`), trimmed:

```text
intent (choice, 385 rows)
  gold: 385 rows (243 from source, 142 from review, 25 with two acceptable labels)
  PASS estimated accuracy 95.8% (95% CI 88.7%–97.9%) from reviews of 60/340 agreeing rows, 45/45 disagreeing rows (min 85%)
       not the headline: on current gold 97.9% (trusts unreviewed rows), on the raw answer key 88.3%
  PASS calibration error 0.043 (raw source gold: 0.053) (max 0.05)
         stated p          n   avg stated   observed
       0.4–0.5           4        0.450      0.750
       ...
       0.9–1.0         311        0.990      1.000
       dial   automated   wrong among automated
       0.50       99.0%                    1.8%
       ...
       0.90       80.8%                    0.0%  ← act
  PASS accuracy among auto-acted 100.0% on 81% of rows at act=0.9 (min 97%)
       most confident mistakes (8 total; high confidence + wrong = dangerous, or a gold error → hunch review):
         # 560 gold=card_acceptance                  got contactless_not_working 0.89           Are contactless payments enabled on my new card?
       most confused (gold → got):
           1  card_acceptance → contactless_not_working
  PASS order stability: 11/300 answers flip (3.7%, 8 within noise band), mean |Δp| of original answer 0.032 (max flip rate 5%)

answers: 685 cached, 0 asked in 0 requests, 0 input tokens, $0.00000
```

Line by line:

- **`gold:`** how many rows have a right answer, and where it came from: the source's gold column, your reviews, or both labels acceptable. Rows marked ambiguous or needing more context are counted as excluded and not scored.
- **`context:`** (only after spot checks marked "needs more context") how many random spot checks needed more than the state shows. A high share means the spec should see more (earlier turns, what happened next), not that the model is wrong.
- **`estimated accuracy`** the headline. It comes from reviewed rows only, with a 95% confidence interval. With an answer key, hunch reviews every disagreement and a random sample of agreements, and weights them to all rows. Without an answer key, it uses the random spot checks alone. The `(min …)` is the `tests:` threshold; `PASS`/`FAIL` compares the estimate with it.
- **`accuracy`** (instead of `estimated accuracy`) when there is no estimate yet: plain accuracy against whatever gold there is. If some rows were reviewed, the next line says `upper bound only, no estimate` and why: reviewing only disagreements can only move accuracy up, so the random spot checks are still missing.
- **`not the headline`** accuracy two other ways, for comparison: on current gold (trusts every unreviewed row) and on the raw answer key.
- **`calibration error`** the average gap between what the model says (`stated p`) and how often it is right (`observed`), weighted by rows. The table shows each band. Observed above stated means the model is too modest; below means overconfident.
- **`AUROC`** (yes/no questions) how well p(yes) separates yes rows from no rows. 0.5 is a coin toss, 1.0 is perfect. Not affected by how rare "yes" is.
- **`dial`** for each confidence threshold: the share of rows your code would act on automatically, and how many of those are wrong. `← act` marks the question's `act`. Yes/no questions get two columns, one per side. The table uses rows with gold; if most gold came from reviewing uncertain rows, it leans toward hard rows.
- **`accuracy among auto-acted`** accuracy on just the rows at or above `act`: the error rate of what your code does unattended.
- **`most confident mistakes`** wrong answers, most confident first. High confidence and wrong is either a dangerous model error or a wrong gold label; review them.
- **`most confused`** the most common (gold → got) pairs.
- **`order stability`** (with `order_stability` in `tests:`) the same rows asked with the options shuffled. Flips inside the noise band (margin under 0.10) are listed but expected.
- **`declined (none_of_these)`**, **`escalated to …`** shown for questions with `none` or `escalate`.
- **`weighted to the population`** shown when the source has sampling weights; every number above is then weighted.
- The last line: answers cached and asked, and the cost.

### `diff`

Real output, BANKING77 (`hunch diff intent.yml --against intent_bare.yml`), trimmed:

```text
answers: 1540 cached, 0 asked in 0 requests, 0 input tokens, $0.00000

══ intent  vs  intent_bare

intent: 77/770 rows flip (15 within noise band)
  probabilities moved: mean |Δ| 0.102, mean Δ p(old answer) -0.021
  gold accuracy on the 770 shared rows with gold 79.0% → 85.5%  (✓ 58 fixed, ✗ 8 broken, 11 wrong both times, 0 without gold)
  paired sign test p=0.000 → significant
  ✓ #  76                activate_my_card 0.92 → card_linking 0.84                           Could you help me reactivate my card? I…
  ✗ # 255           fiat_currency_support 0.66 → exchange_via_app 0.91                       How do I change currencies to euros?
    # 268                   exchange_rate 0.68 → exchange_via_app 0.94                       I want to make a currency exchange to E…
  … 65 more
```

- **`rows flip`** rows whose answer changed, and how many of those changes are within the noise band (either side's margin under 0.10: re-asking would flip them too).
- **`N rows newly reach it, M no longer do`** a `where` upstream changed which rows this judgment sees.
- **`probabilities moved`** how far answers moved, not just which labels changed. `mean |Δ|` is the size of the move; `mean Δ p(old answer)` is its direction (negative: the new spec is less sure of the old answer; for yes/no questions, the change in p(yes)).
- **`gold accuracy … →`** accuracy of old and new on the shared rows with gold. Flips split into ✓ fixed, ✗ broken, wrong both times, and without gold.
- **`paired sign test`** whether fixed vs broken is more than chance. `NOT significant` means get more gold before believing the change.
- Each flip: ✓ fixed, ✗ broken, blank for no gold or wrong both times; `~noise` marks noise-band flips (listed last).
- Other forms: `unchanged (same keys, 0 calls)`, `new question`, `renamed from 'x'` (matched by answer keys), and `moved by upstream changes` when this spec is identical and only its inputs changed.

Both sides use today's reviews: gold belongs to the rows, not to a spec version.

### `review`

See [Review](/guides/review) for the screen and keys. `--list` prints one row per item:

```text
review queue: 112 disputed, 30 audit
  disputed  #  281 intent     card_arrival 1.00                    gold=card_delivery_estimate   my card was not in the mail again can you advise?
```

Kind, row id, question, the model's answer and confidence, the answer key (`-` if none), and the start of the row.
