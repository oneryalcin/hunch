Suppose your program sends each support ticket to a model with one question: which team should handle this? The model answers *billing*, with confidence 0.93.

Is that right? For one ticket, you can read it and check. But the program asks the same question of thousands of tickets a week, and you cannot read them all. What you want to know is how often the answer is right, and whether that changes when someone edits the question.

An answer key helps less than you might expect. On a public set of 385 banking messages, the model disagreed with the dataset's key 45 times. A panel of AI reviewers checked those 45 one by one: the key was wrong in 20, the model in 5, and the other 20 could reasonably go either way. A label is someone else's judgment, and it can be wrong too. To measure a model you end up reading some rows yourself.

hunch is built around that problem, from three ideas.

## The question is written down

The question, its options and the columns the model may see go in a YAML file called a spec:

```yaml ticket_triage.yml
judgment: ticket_triage
model: jev-1.13.0
source: tickets.csv
key: id
state: [subject, body]

questions:
  department:
    type: choice
    instructions: Which team should handle this support ticket?
    criteria:
      billing: Problems with money already charged or owed
      technical: Something is broken, slow, or misbehaving
      sales: Buying more or buying differently
    gold: gold_department
```

The spec lives in git next to your code. If you have used dbt, it plays the part of a model there: a file that is run, tested, and changed through review.

## Every answer is kept

`hunch run` asks the question of every row and stores each answer under its exact input. Run it again and the answers come from the store at no cost. Change one question and only that question is asked again.

## Accuracy is measured against gold

Gold is what you count as correct: the answer key, if there is one, and the rows you have reviewed. `hunch review` picks the rows worth reading, such as where the model and the key disagree, plus a random sample. Your verdicts become gold.

`hunch test` then reports accuracy as a range, because 24 reviewed rows tell you less than 240. When you change a question, `hunch diff` lists the rows whose answer would flip, before you ship the change.
