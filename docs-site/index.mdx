A coding agent wants to remove a broken Python environment. The model says the command is destructive at 0.74; the answer key says no. Which answer should your guard trust?

That is one of 38 real commands in the [quickstart](/quickstart). To build a guard you can rely on, you need to record the question and what the model saw, review disagreements, measure errors on known cases, and inspect what an edit changes. A probability by itself does not establish how often an answer is right.

**hunch keeps the question in a versioned spec, measures its answers against evidence, and shows which answers meet your bar for acting.**

![A person considers a checked card, a question card and a decision still to make](/images/decision-review.webp)

## Decision engineering

dbt helped make scattered SQL into a practice: write transformations once, keep them in git, run them in several places, and test changes. hunch brings that discipline to model judgments:

- **Write the question once.** Its wording, its possible answers and what the model may see go in a YAML file in git. The same file answers a million rows in a batch, a column in a SQL query or a dbt model, or one row inside your app as it happens, from the same cache.
- **Choose where to act.** Every answer comes with a probability. The spec sets a confidence bar; your application decides what happens above it and sends the rest to a person. On labelled or reviewed rows, `hunch test` shows how many answers clear the bar and how many of those are wrong.
- **See what a change does.** `hunch diff` shows which answers an edited spec would flip. In CI, `hunch test` fails when a configured check fails. An app that relies on an answer's name is protected from a rename.
- **Make it better from use.** `hunch review` shows you the few rows where a verdict teaches the most. Your verdicts become the answer key the next test measures against.

## Where decisions live

The same shape, a question, a typed answer, a bar for acting and a person for the rest, turns up across a whole company:

| Where | Decisions like |
| --- | --- |
| Coding and AI agents | Is this command safe to run? Did the agent really fix it? Should it stop or go on? [Did this change leave a comment wrong?](/cookbooks/stale-comments) |
| Data pipelines | Turn text into columns you can query: which calls mention churn, which reviews are about quality, which contracts auto-renew. [Which records in two lists are the same thing?](/cookbooks/product-matching) |
| Product | Does this post break the rules? Is this user eligible? Which requests are urgent? |
| Operations and security | Is this alert worth paging for? Is this email phishing? Should this access request be approved? |
| Risk and compliance | Is this expense within policy? Does this document meet the requirement? Is this claim covered? |
| AI output checks | [Is the answer supported by its source?](/cookbooks/rag-answers) Does it leak personal data? Did it follow the instructions? |

The same workflow can serve each case: define the answer, inspect the evidence, and decide what may happen without a person.

## How it works

Write a spec, run it on rows, review a sample, and test the answers. Before changing the spec, use `diff` to see which rows would change. [Concepts](/concepts#how-the-pieces-meet) shows the decision and review paths.

Here is part of the command guard. It reads a coding agent's sessions and asks about each shell command before it runs:

```yaml command_guard.yml
judgment: command_guard
model: jev-1.13.0
source: traces(sessions/*.jsonl)
view: commands
key: id
state: [request, cwd, command]

questions:
  destroys:
    type: noul  # yes/no question
    instructions: Would running `command` delete, overwrite or reset something in a way that is hard to undo?
    act: 0.90
  sends_out:
    type: noul
    instructions: Would running `command` send code, files or data from this machine to another one?

examples:
  - name: wipes the home folder
    row: {request: clean up my machine, cwd: /home/USER/app, command: rm -rf ~}
    expect: {destroys: "yes"}
```

`hunch run` asks every row and stores each answer under its exact input. An unchanged request uses the stored answer; editing one question re-asks that question. Inside your app, [`hunch.judge()`](/guides/use-in-your-app) answers one row at a time from the same spec and store. A [Pydantic AI agent](/guides/pydantic#from-a-pydantic-ai-agent) on a decision model can be recorded and tested on past rows. [`hunch docs`](/guides/share) makes a project report for whoever signs off on the policy.
